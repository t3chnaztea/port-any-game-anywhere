# Launch plan

Launch the project around evidence that it helps finish a port. The name attracts attention. The first demonstration must make its practical meaning clear.

This document is a plan. No release, announcement, outreach, or publication is authorized by its existence.

## Public beta gate

Release v0.1 as a public beta only after the required gates in [STATUS.md](../STATUS.md) close. Those include clean installation, live Codex evaluation, failure and interruption cases, stale-input rejection, independent final-claims review, and actual target-device checks for the worked examples.

The planned recovery demonstration requires a fresh unpublished fixture derived from the Switchboard design or another original game. The public Switchboard code is regression material and cannot establish no prior source exposure. The external Fifteen reproduction checks the source-led workflow. Keep its existing upstream browser port visible in the description.

If a required pilot cannot run because its tools or device are unavailable, retain development-snapshot status. Do not replace the missing run with expected output, a mocked pass, or a promotional video.

## Release package

Prepare a versioned source archive containing the complete skill directory, references, templates, helpers, license, and notices. Provide one tested copy command and an explicit invocation example. Review archive contents for private paths, proprietary assets, secrets, and stale acceptance records.

Publish the exact evaluation revision and environment. Show the denominator behind coverage counts. Identify source inspection, automated checks, browser results, and actual device results separately. List known limitations near the installation instructions.

## Demonstrations

1. **A missing path becomes visible.** Start from a working scene whose save recovery or alternate mode is broken. Show the inventory entry, reproduction, fix, independent check, and current evidence link.
2. **A binary becomes a verified port.** Use a fresh unpublished fixture with evaluator-held source and an unexposed agent. Show the enforced source boundary, recovered C build, browser controls, persistence and final path comparison. Freeze results before source disclosure. State the limits. The current public Switchboard fixture supports reproducible regression demonstrations only.
3. **An interruption does not become a pass.** Stop a run, change a relevant input, then show why the old result cannot close the new gate. Resume only unchanged work with intact evidence.
4. **An impressive number gets a precise meaning.** Show a test count beside the finite required-path inventory. Explain what remains partial or untested. Do not present command counts as game completeness.

Use short captioned video or text-and-screenshot sequences. Supply the commands, fixture revision, and expected outputs. Include a text transcript. Do not depend on motion, color, or an image alone to communicate a result.

## Announcement sequence

First, have five fresh testers follow the first-use guide without coaching after prerequisites are available. At least four must produce a useful, reviewable port plan within 20 minutes. Retain the assessment criteria and each outcome. Ask where they stall and which evidence they cannot reproduce. This is an onboarding acceptance gate, not a population-wide outcome claim.

After beta acceptance, publish one release note with a concrete before-and-after example, the installation path, the evaluation report, and the known limits. Prepare one runnable Show HN after the beta is accepted. Check the community’s current rules before posting. Share it only in relevant communities whose rules allow project posts. Do not request upvotes. The primary audience is people already doing a port, not people seeking a one-click conversion service.

Use the Sonic case study to explain the process’s origin. Use the redistributable examples to prove the current skill. Do not promote Sonic’s historical automated results as validation of this repository.

## What to measure

Track successful first use, time to a reviewable plan, confusing steps, reproducible defect reports, completed evaluation runs, and independently accepted adapters. Record bounded paired-task cost data without claiming savings from too few trials.

Stars, downloads, comments, and social reach can describe attention. They do not prove port quality, maintainability, or that presentation caused adoption. Compare claims with actual use and retained evidence.
